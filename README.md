# DDD の書き方の違いを検証する

## 対象の記載方法

- トランザクションスクリプト
- アクティブレコード
- ドメインモデル

## 題材：ノートにタグを付ける

業務ルールは3つだけ。

1. アーカイブ済みのノートにはタグを付けられない
2. タグは1つのノートに5個まで
3. 同じタグを2回付けられない

コードは1パターン＝1フォルダ、1層＝1ファイル

```
src/
├── main.rs              パターン番号で振り分けるだけ
├── pattern1/            トランザクションスクリプト
│   ├── presentation.rs
│   ├── application.rs
│   └── infrastructure.rs
├── pattern2/            ＋アクティブレコード
│   ├── presentation.rs
│   ├── application.rs
│   └── infrastructure.rs
└── pattern3/            ドメインモデル
    ├── presentation.rs
    ├── application.rs
    ├── domain.rs        ← ドメイン層があるのはパターン3だけ
    └── infrastructure.rs
```

## 動かし方

```bash
cd literature/code/ddd-layers
cargo run -- 3 create n1          # パターン3でノートを作る
cargo run -- 3 add-tag n1 rust    # タグを付ける
cargo run -- 3 add-tag n1 rust    # → エラー: タグ「rust」はもう付いています
cargo run -- 1 archive n1         # パターン1でアーカイブ
cargo run -- 2 add-tag n1 ddd     # → エラー: アーカイブ済みのノートにはタグを付けられません
cargo run -- 3 list
cat notes.txt                     # 保存されたテキストファイル
cargo test                        # パターン3の業務ルールのテスト（ファイルを使わない）
```

3つとも同じ `notes.txt` を同じ形式（1行＝`id|archived|version|tag1,tag2`）で読み書きするので、パターンを混ぜて操作できる。
外から見た動きは3つとも同じで、違うのは中の作りだけ。

## ポイント

1. 業務ルールがどのファイルに書いてあるか
2. 保存形式を知っているのはどのファイルか

| パターン                   | 1   | 2   | メモ |
| -------------------------- | --- | --- | ---- |
| トランザクションスクリプト |     |     |      |
| アクティブレコード         |     |     |      |
| ドメインモデル             |     |     |      |

## まとめ

### 3つを並べると

|                               | プレゼンテーション層 | アプリケーション層         | ドメイン層                       | インフラ層                       |
| ----------------------------- | -------------------- | -------------------------- | -------------------------------- | -------------------------------- |
| 1. トランザクションスクリプト | CLI                  | 業務ルール＋保存形式＋手順 | 無し                             | 行を読む／書くだけ               |
| 2. ＋アクティブレコード       | CLI（1と同じ）       | 業務ルール＋手順           | 無し                             | `NoteRecord`（データ＋保存形式） |
| 3. ドメインモデル             | CLI＋部品の組み立て  | 手順だけ                   | `Note`（業務ルール）＋保存の約束 | 約束の中身（保存形式）           |

### 4つの層の役目（3つに共通）

- **プレゼンテーション層**：外からの入力（今回は CLI の引数）を受け取り、結果を見せる。入力の形式チェック（空白や `|` を含まないか）もここ。これは業務ルールではなく「入力として受け付けられるか」のチェック
- **アプリケーション層**：1回の操作の手順と、その操作を「全部反映するか、何も反映しないか」にまとめる役。3つとも `読む → 何かする → 保存` の形をしている。本の 6章「基本的にはアプリケーション層のクラスはトランザクションスクリプトです」はこのこと。ドメインモデルにしてもトランザクションスクリプトは消えず、「何かする」の中身が「ルールを自分で書く」から「集約に頼むだけ」に薄くなる
- **ドメイン層**：業務ルール。パターン3にしか無い
- **インフラ層**：保存の仕組み。今回はテキストファイル。一時ファイルに書いてから置き換えることで、途中で失敗しても元のファイルが壊れないようにしている（DB のコミットの代わり）

### どれを選ぶか

- ルールがほとんど無い・機能が少ない → トランザクションスクリプト
- ルールは少ないが、データの形が複雑（テーブルをまたぐ） → ＋アクティブレコード
- ルールが多く、あちこちから同じデータを変更する → ドメインモデル
